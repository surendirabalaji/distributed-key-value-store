The Mental Shift: Peer-to-Peer
In a standard gRPC app, you have one Server and many Clients.
In Raft (and this codebase), every node is both a Server and a Client simultaneously.

*   As a Server: It listens on a port (defined in config.hpp) to receive requests from other nodes.
*   As a Client: It holds a connection (Stub) to every other node in the list (peers_ map) to send requests.

Codebase Walkthrough (RPC Perspective)

1. The Interface (proto/raft.proto)
This is where you define the contract. Since you know gRPC, you know this is the single most important file to start with.
*   Current State: Implemented.
*   Goal: You need to define the methods for Raft here.
    *   RequestVote: "I want to be leader, please vote for me."
    *   AppendEntries: "I am leader, here is data (or a heartbeat)."

2. The "Server" Side (inc/rafty/raft.hpp & src/raft.cpp)
This class represents a single Raft node.
*   The "Main" Loop: void run() in src/raft.cpp. unlike a stateless web server that just waits for requests, a Raft node must be active. It needs a loop or timer to check: "Have I heard from the leader lately? No? Time to start an election!"
*   The Service Implementation: You will need a class (usually strictly internal or a friend class) that implements the RaftService::Service interface generated by protoc.
    *   When another node calls RequestVote, this logic checks your state (Term, Log) to decide true (Yes) or false (No).

3. The "Client" Side (peers_ map in raft.hpp)
Look at inc/rafty/raft.hpp:
std::unordered_map<uint64_t, RaftServiceStub> peers_;
*   This map holds the gRPC Stubs.
*   peers_[1]->RequestVote(...) is how you ask Node 1 for a vote.
*   Crucial detail: All these RPCs happen concurrently. When you start an election, you loop through peers_ and fire off async requests to everyone.

The "Lab 1" Task: Leader Election
The goal is to get one node to transition from Follower -> Candidate -> Leader.

Here is the flow you will implement:

1.  The Timer (The Trigger):
    *   Every node starts as a Follower.
    *   It expects a "Heartbeat" (an empty AppendEntries RPC) from the Leader.
    *   If election_timeout (randomized, e.g., 150-300ms) passes without a heartbeat, the node assumes the leader is dead.

2.  The Election (The Client Actions):
    *   The node increments its current_term.
    *   It votes for itself.
    *   It uses the peers_ stubs to send RequestVote RPCs to everyone else.

3.  The Vote (The Server Actions):
    *   Other nodes receive the RequestVote RPC.
    *   They check: "Is this term higher than mine? Have I voted yet?"
    *   They reply Yes/No.

4.  Becoming Leader:
    *   If the Candidate gets votes from a majority (e.g., 2 out of 3), it becomes Leader.
    *   It immediately starts sending Heartbeats (AppendEntries) to stop others from timing out.

Summary of where you will work
1.  proto/raft.proto: Define the arguments and return values for RequestVote and AppendEntries.
2.  src/raft.cpp:
    *   Implement the timer logic in run().
    *   Implement the RPC handler logic (Server side).
    *   Implement the logic to send RPCs (Client side).
3.  inc/rafty/raft.hpp: Add state variables (current_term, voted_for, role, last_heartbeat_time).
